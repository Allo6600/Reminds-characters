00結論サマリ

この設計で重要な判断は3つです。

判断 1

コアを純粋な TypeScript パッケージに切り出す

レベル判定と既知単語管理は環境に依存しない純関数にできる。ストレージだけをアダプタで差し替え、PC拡張とスマホで同じコードを動かす。

判断 2

モバイルは React Native

上のコアを「移植」ではなく import するため。Kotlin で書き直すと判定ロジックが二重管理になり、必ず食い違う。

判断 3

PC版が主、モバイルは従

後述の技術的制約により、スマホ単独で高精度に字幕を取ることは原理的に難しい。ここを楽観視すると計画が崩れる。

先に潰すべき最大のリスク

①Netflix の上に Android オーバーレイを出せるか／②BGM混じりの映画音声で音声認識がどれだけ使えるか。この2つの結果次第でモバイル版の位置づけが変わるため、実装より先に検証します（第12章）。

01スコープと前提

作るもの

  • PC版 — Chrome 拡張。Netflix Web の字幕を取得し、未知単語を検出・蓄積する
  • モバイル版 — Android アプリ。マイク経由の音声認識でテキスト化し、オーバーレイ字幕として表示。タップで単語カード生成
  • 共有コア — レベル判定・既知単語管理・単語正規化
  • 復習 — 未知単語リスト、SRS（間隔反復）、Anki/CSV エクスポート

作らないもの

  • 動画・音声の保存（明示的な非目標。音声はテキスト化した瞬間に破棄）
  • 字幕ファイルそのものの保存・再配布
  • Netflix 以外のプラットフォーム対応（差し込める設計にはするが実装しない）
  • iOS 版（理由は第7章）

「Language Reactor とロジック共有」の解釈

Language Reactor はサードパーティ製品なので、その内部コードに手を入れることはできません。取れる道は2つです。

  • (A) 自作のPC拡張を作り、そこと共有する ← 本設計はこちら
  • (B) Language Reactor をそのまま使い、その単語リスト書き出し（CSV/JSON）を取り込む口だけ用意する

(B) は Phase 1 の暫定手段として有効なのでインポート機能は作ります。ただし本命は (A) です。

02全体構成

レイヤ構成

@vocab/core            純粋TS。I/Oを持たない
  ├─ normalize/        トークナイズ、レンマ化、固有名詞除外
  ├─ level/            CEFR-J・頻度からの難易度判定
  ├─ vocab/            既知/未知/学習中の状態遷移
  ├─ srs/              間隔反復のスケジューリング
  └─ ports/            ストレージ・辞書のインタフェース定義（実装なし）

@vocab/data            ビルド時に生成される静的JSON
@vocab/storage-idb     IndexedDB 実装（PC拡張用）
@vocab/storage-sqlite  SQLite 実装（モバイル用）
apps/extension         Chrome 拡張 (MV3)
apps/mobile            React Native (Android)

コアは ports/ にインタフェースだけ置き、実装を持ちません。これで「同じ判定が PC でもスマホでも1行も違わずに動く」ことが保証され、テストもコアだけで完結します。

03データフロー

PC版 — 字幕1行が未知単語になるまで

実装上の落とし穴

Chrome 拡張の Content Script は netflix.com のオリジンで動くため、そこで IndexedDB を開くと「Netflix のデータベース」になります。永続化は必ず Service Worker（拡張オリジン）側で行うこと。ここを間違えると、Netflix 側のストレージ削除で学習データが消えます。

モバイル版 — 音から単語カードまで

音声は固定長リングバッファ上にのみ存在し、ファイル化・アップロードを一切行いません。オンデバイス STT を既定にすることで、この保証をコードレベルで担保します。

04ロジックの共有
—— 検討事項 1 への回答

共有できます。レベル判定・既知単語管理は「単語列 + 参照データ」だけで決まる純関数なので、環境非依存に書けます。阻害要因は2つだけです。

阻害要因対策
言語の違い（TS と Kotlin）モバイルを React Native にして TS に統一。Kotlin はオーバーレイ・マイク・STT のネイティブモジュールのみ
ストレージAPIの違い（IndexedDB と SQLite）コアは VocabRepository インタフェースにのみ依存し、実装を注入する

ポート定義（コアが要求する契約）

export interface VocabRepository {
  getKnownLemmas(): Promise<Set<string>>;        // 起動時に一括ロード
  getWord(lemma: string): Promise<WordRecord | null>;
  upsertWord(w: WordRecord): Promise<void>;
  addEncounter(e: EncounterRecord): Promise<void>;
  listByStatus(s: WordStatus, opt?: Page): Promise<WordRecord[]>;
  listDue(now: number): Promise<WordRecord[]>;    // SRS用
}

export interface LevelDataSource {
  lookup(lemma: string): LevelInfo | undefined;   // 同期。メモリ常駐前提
}

判定アルゴリズム

function judge(token: Token, ctx: JudgeContext): Verdict {
  if (ctx.known.has(token.lemma))  return 'known';
  if (isProperNoun(token))         return 'skip';   // 人名・地名
  if (isFunctionWord(token.lemma)) return 'skip';   // 冠詞・前置詞
  if (token.lemma.length <= 2)     return 'skip';

  const info = ctx.levels.lookup(token.lemma);
  if (!info) return 'unknown';       // 辞書に無い＝低頻度＝難語

  const tooHard =
    (info.cefr && cefrRank(info.cefr) > cefrRank(ctx.userLevel)) ||
    (info.zipf && info.zipf < ctx.zipfThreshold);

  return tooHard ? 'unknown' : 'known';
}
体感品質を最も左右する箇所

ドラマは登場人物名だらけなので、固有名詞を弾かないと未知単語リストが人名で埋まります。3段構えで対処します —— ①品詞タガーで ProperNoun 判定、②文中で大文字始まり かつ レベル辞書に無い、③作品ごとの名前リストを自動学習（同一作品内で3回以上出た未知の大文字語は固有名詞とみなす）。

英検レベルについての注意

旺文社「でる順パス単」等の市販単語リストは著作物であり、取り込み・再配布はできません。英検級で表示したい場合は、英検協会が公表している英検↔CEFR 対応を使い、CEFR-J のレベルから換算します。つまり保持するのは CEFR、表示だけ英検に変換する。権利上クリーンで、UIの分かりやすさも保てます。

英検3級準2級2級準1級1級
CEFR（概ね）A1A2B1B2C1

ビルド時のデータパイプライン

tools/build-leveldata/
  ├─ fetch/      CEFR-J(xlsx) / NGSL(csv) / TSL(csv) / SUBTLEX(txt)
  ├─ normalize/  レンマ化・表記ゆれ統合・重複解決
  ├─ merge/      優先順位: CEFR-J > NGSL段位 > Zipfのみ
  └─ emit/       levels.json  (gzip後 約300〜500KB)
{ "l": "reluctant", "c": "B2", "z": 3.9, "t": 0, "p": "adj" }

l=lemma, c=CEFR, z=Zipf頻度, t=TSL順位, p=品詞。キーを1文字にするだけで配布サイズが2〜3割縮みます。実行時は Map としてメモリ常駐（数MB程度）。

06PC版（Chrome 拡張）

字幕の取得方法 — 2案

案方法長所短所
採用 A. DOM監視 .player-timedtext を MutationObserver で監視 実装が単純で堅牢。表示中の字幕がそのまま取れる 表示された分しか取れない。早送りで取りこぼす
保留 B. マニフェスト傍受 JSON.parse をフックし字幕トラックURLを取得、TTMLを丸ごと取る エピソード全文＋タイムコードが一度に入手できる 内部仕様変更で壊れやすい。字幕全文の保持は権利上グレー

A を採用。B の「全文を落として保存する」挙動が非目標（字幕を保存しない）と衝突するためです。A なら「視聴した箇所の、単語と文脈文だけ」が残る形になり、目的にも権利上も素直です。

拡張の構成（Manifest V3）

content.ts   字幕DOM監視 + 未知語の下線描画 + クリック処理
worker.ts    判定エンジン・IndexedDB・レベルデータ常駐
popup.tsx    今エピソードの未知語サマリ
options.tsx  レベル設定・キャリブレーション・エクスポート
review.tsx   復習（SRS）画面

視聴体験を壊さないための配慮

  • ハイライトは細い下線のみ。背景色は使わない（視聴の邪魔になる）
  • ポップアップは一時停止時のみ自動表示。再生中はクリックしたときだけ
  • 既定は「収集だけしてエピソード終了時にまとめて提示」モード

07モバイル版（Android）

まず、正直な技術評価

依頼の想定アプローチ（マイク → STT → 字幕表示）は唯一実現可能な経路ですが、精度に明確な限界があります。他の一見良さそうな方法が全て塞がれていることを先に共有します。

代替案可否理由
画面キャプチャして字幕をOCR不可Netflix は DRM 保護のため FLAG_SECURE を使用。MediaProjection では黒画面しか取れない
端末内部音声を直接キャプチャ
AudioPlaybackCapture (API 29+)		ほぼ不可再生アプリが許可した音声しか取れない。DRM動画アプリは通常 ALLOW_CAPTURE_BY_NONE。Phase 0 で実測
アクセシビリティサービスで字幕を読む不可字幕は動画フレーム内に描画されており、Viewツリー上にテキストとして存在しない
マイクで拾って STT可スピーカー再生が前提。BGM・効果音・複数話者で認識率が落ちる
位置づけの結論

モバイルは「補助的な収集端末 兼 主要な復習端末」とします。単語収集の主戦場は PC 版。これは妥協ではなく投資対効果として合理的です —— 復習こそスマホの独壇場なので。

STT エンジンの選定

候補動作コスト評価
Voskオンデバイス無料モデル約50MB、連続認識に強い。第一候補
whisper.cpp (base.en)オンデバイス無料精度は上。発熱・電池・遅延が課題。第二候補
Android SpeechRecognizer端末依存無料連続認識に制限。無音で切れる。不向き
Cloud STT通信従量精度最良だが音声が外部に出る。既定にしない

オーバーレイ実装

  • TYPE_APPLICATION_OVERLAY + SYSTEM_ALERT_WINDOW 権限
  • 画面下部に固定した半透明の字幕バー（歩き回らせない。字幕は動かさない）
  • 単語ごとに Spannable のクリック領域を持たせ、タップでカード表示
  • FLAG_NOT_FOCUSABLE を付け、Netflix の再生操作を阻害しない
既知のリスク

Android 12 以降、アプリは hideOverlayWindows() で他アプリのオーバーレイを隠せます。Netflix がこれを使っている場合、字幕バーが表示されません。Phase 0 の最優先検証項目です。

音声の扱い（非保存の担保）

マイク → AudioRecord (16kHz mono)
       → 固定長リングバッファ（直近3秒 = 96KB）
       → STT へ push
       → バッファは上書きされ続ける
       → ファイルI/Oのコードを一切持たない

「保存しない」は設定項目ではなくアーキテクチャで保証します。書き出しの実装が存在しません。

iOS を初期スコープ外にする理由

iOS には他アプリの上に重ねる仕組みが存在しません。加えてバックグラウンドでのマイク常時使用も制約が強く、「Netflix を見ながら字幕を重ねる」という中心体験が成立しません。iOS 対応するなら「集めた単語を復習するだけのアプリ」になります。

08既知単語登録の UX
—— 検討事項 3 への回答

最大の課題

普通に作ると、ユーザーは既知の単語を数千回タップさせられます。この種のツールが続かない最大の理由がこれです。したがって「1語ずつ登録する UI」より先に一括で推定する仕組みを作ります。

レベルキャリブレーション（初回、約2分）

  • Zipf 頻度で層別サンプリングし、50語のテストで語彙規模を推定
  • 「あなたは約8,000語レベル（英検2級相当）」と提示し、しきい値の初期値に反映

日常運用の登録フロー

場面操作結果
字幕上のハイライト語長押し（PCは K キー）即 known。トーストで「元に戻す」
単語カード上「知ってる」1回known。カードを閉じリストからも消える
復習リスト右スワイプ = 知ってる／左 = 残す一覧を高速に間引ける
固有名詞だった「名前だった」ignored。作品別の名前リストにも追加

「元に戻す」は必ず用意します。誤タップで既知にすると二度と出てこなくなり、静かに学習機会を失うためです。

状態遷移

        初出
         ↓
     [unknown] ──「覚えたい」──→ [learning] ──SRS合格──→ [known]
         │                          │
         └──「知ってる」────────────┴──────────────→ [known]
         │
         └──「名前だった/記号」───────────────────→ [ignored]

09データモデルと IndexedDB スキーマ
—— 検討事項 4 への回答

設計方針

  • lemma（小文字の原形）を単語の主キーにする。表層形は出現記録側に持つ
  • 単語（words）と出現（encounters）を分離。同じ語が何度出ても単語は1レコード
  • 全レコードに updatedAt / deviceId / deleted を持たせ、Phase 5 の同期に最初から備える（後付けは非常に高くつく）

スキーマ定義（db version 1）

// ---------- words: 単語1件 = 1レコード ----------
interface WordRecord {
  lemma: string;            // ★keyPath。小文字・原形
  pos?: string;
  cefr?: 'A1'|'A2'|'B1'|'B2'|'C1'|'C2';
  zipf?: number;
  status: 'unknown' | 'learning' | 'known' | 'ignored';
  seenCount: number;
  firstSeenAt: number;
  lastSeenAt: number;
  srsDue?: number;          // 次回出題時刻(epoch ms)
  srsInterval?: number;     // 日数
  srsEase?: number;
  updatedAt: number;        // 同期用
  deviceId: string;
  deleted?: boolean;        // トゥームストーン
}
// indexes: by_status, by_due(srsDue), by_cefr,
//          by_updated(updatedAt), by_lastSeen

// ---------- encounters: 出会った文脈 ----------
interface EncounterRecord {
  id: number;               // ★autoIncrement
  lemma: string;
  surface: string;          // 実際の表示形 (was, running)
  sentence: string;         // 文脈文（学習価値の中心）
  sourceId: string;
  positionMs?: number;
  capturedAt: number;
  origin: 'pc' | 'mobile';
  confidence?: number;      // STT由来のときの信頼度
}
// indexes: by_lemma, by_source, by_captured

// ---------- sources: 作品・エピソード ----------
interface SourceRecord {
  id: string;               // ★ "netflix:80192098"
  platform: 'netflix';
  title: string;
  season?: number;
  episode?: number;
  firstWatchedAt: number;
}

// ---------- cards / settings / properNouns ----------
interface CardRecord {
  lemma: string;            // ★keyPath
  definitionJa?: string;
  definitionEn?: string;
  examples: string[];
  phonetic?: string;
  generatedBy: 'dict' | 'llm';
  updatedAt: number;
}

なぜこの形か

  • words.by_due があると、復習対象の抽出が IDBKeyRange.upperBound(now) 一発で済む
  • encounters を分離することで「この単語、あのドラマのあの場面のやつだ」という記憶に最も効く情報が残る。単語帳アプリとの決定的な差はここ
  • by_updated は同期の差分抽出用。これがないと毎回全件比較になる

モバイル側（SQLite）

同じ論理スキーマを SQLite のテーブルとして持ちます。カラム名・型は 1:1 対応させ、@vocab/storage-sqlite が VocabRepository を実装します。コアから見れば両者は区別できません。

インポート／エクスポート

  • エクスポート — JSON（全データ）／CSV／Anki 形式（表: 単語、裏: 語義+例文+出典）
  • インポート — 上記 JSON、および Language Reactor 等の CSV（列マッピング画面付き）

10単語カードの生成

  • 一次情報はオフライン辞書（EJDict）。通信ゼロ・即応答で視聴体験を止めない
  • LLM は「補強」に限定。字幕の文脈文を渡して「この場面でのこの語の意味」を生成。1エピソード分をまとめて投げればコストは実用範囲
  • 生成結果は cards にキャッシュし、同じ語で二度課金しない

12リスクと Phase 0 での検証

最重要

実装に入る前に以下を1〜2週で潰します。ここで結果が出ないまま先に進むと、作ったものが動かない可能性があります。

#検証項目方法方針転換の基準
R1Netflix の上にオーバーレイを出せるか最小アプリで字幕バーを出し、Netflix 再生中に表示・タップを確認表示されない → モバイルは「復習専用アプリ」に転換
R2映画音声の STT 精度会話劇・アクション・ドキュメンタリー各10分を Vosk / whisper で書き起こし、公式字幕と WER 比較WER > 50% → 常時検出を諦め、タップ時のみ高精度認識に縮退
R3内部音声キャプチャの可否AudioPlaybackCapture を Netflix 再生中に実行取得できれば R2 が大幅改善（期待値は低い）
R4Netflix Web の字幕DOM構造映画/シリーズ/アニメ で .player-timedtext の有無を確認画像字幕が多い → 対応タイトルを明示する方針に
R5レベルデータの実用性実際の1エピソードを判定し、未知語候補を人手評価誤検出が3割超 → 除外ロジックを強化

14将来の同期
—— 検討事項 5 への回答

十分に実現可能で、しかも「後から足せるように今すぐ備えておくべき」ものです。段階的に3案あります。

段階方式インフラ手間
即日JSON エクスポート/インポート不要最小。Phase 1 で入れる
推奨 現実解Google Drive appDataFolder不要（ユーザーの Drive のアプリ専用隠し領域）中
本格Supabase / Firebaseサーバ・認証・費用大。個人利用には過剰

推奨は Google Drive の appDataFolder。サーバー運用ゼロ、費用ゼロ、データはユーザーの手元、の三拍子が揃います。

競合解決はレコード単位の last-write-wins で十分です（同じ単語を2端末で同時編集する頻度は極めて低いため）。そのために必要なのが第9章の updatedAt / deviceId / deleted です。

pull:  自分の lastSyncAt より新しいリモートレコードを取得
merge: 同一キーなら updatedAt が大きい方を採用
push:  lastSyncAt 以降に更新したレコードを送信
事故を防ぐ特別扱い

known は「一度知っていると宣言したら基本戻らない」性質なので、マージ時はknown を優先します。片方で known にしたのに古いレコードで unknown に戻る事象を防げます。

15法務・プライバシー上の留意点

  • 字幕の全文保存・再配布はしない。保持するのは「単語」と「その単語を含む1文」に限定し、エクスポートにも全文を含めない
  • 音声は保存しない。ファイル書き出しの実装自体を持たないことで担保する
  • 市販の英検単語リストは取り込まない。CEFR-J からの換算表示に留める
  • CEFR-J / SUBTLEX は非商用利用条件。個人学習用途に留め、公開・商用化する場合はライセンスを再確認する
  • Netflix の利用規約は自動化に制限がある。個人の学習目的に留め、収集データの公開・配布は行わない
